## 1. 参考 CCswitch 后确定的可借鉴能力

- 将真实模型路由 ID（slug）与界面显示名称分离。
- 通过模型目录让 Codex 在同一供应商的多个模型之间切换。
- 保存并恢复每个配置自己的模型状态和模型目录。
- 本项目只借鉴设计思路，没有复制 CCswitch 源码。
- 未引入 CCswitch 类型的协议代理、请求转换或多供应商自动路由。

## 2. 商议后确认的产品目标

- 从供应商兼容的 `/models` 接口读取 API Key 可用模型。
- 模型列表按配置独立保存；再次获取时覆盖该配置的完整列表。
- 当前配置页只读展示实际 live 配置；新增和编辑配置使用同一套模型列表保存事务。
- 保留模型手动输入；若已有配置助手目录，手动模型会追加而不是清空目录。
- 模型显示名称由后台根据真实 slug 自动生成，不要求用户维护。
- 新增或编辑只保存配置库；编辑活动配置后标记待应用，双击时才写入 live 配置并启动或重启。
- 切换配置时恢复目标 Provider、API Key、Base URL、启动默认模型、默认 `model_reasoning_effort` 和完整模型目录。
- Codex 对话内临时切换只影响对应对话，不自动覆盖配置库；不读取或修改 Codex 私有应用数据库。
- API→官方登录→API 往返不删除聊天记录或会话数据。
- 官方 OpenAI Provider 的模型显示与能力完全交给 Codex，不使用配置助手目录。
- 自定义 Provider 仅对原生缓存中精确匹配的 slug 复用整条 Codex 元数据，其他模型安全降级。

## 4. 本轮发现并修复的缺陷

1. 选择模型会调用清空目录逻辑，导致刚获取的完整列表立即丢失。
2. 当前页依次写当前配置和配置库，第二次失败时第一处不会恢复。
3. 新建/编辑先保存或应用配置，再单独写模型目录，形成半成功状态。
4. 新建配置错误继承当前供应商的模型目录。
5. 切换配置只根据默认模型重建一个目录条目，完整列表被压缩。
6. 切换未恢复 `model_reasoning_effort`，A 的推理强度可能遗留到 B。
7. 活动配置路径未验证身份，极端情况下可能把当前 Provider 状态写进旧配置。
8. external/none/owned 三种目录状态没有被完整区分。
9. 部分事务只捕获磁盘错误，配置冲突或损坏目录可能在首个文件写入后未触发回滚。
10. 运行中的 Codex 在目标配置投影后才关闭，退出持久化会用旧内存凭据覆盖目标 `auth.json`，造成目标 Provider 与错误 Key 组合并持续重连；最终方案改为运行中拒绝切换，不再由配置切换管理 Codex 生命周期。
11. 模型目录把当前推理强度写成唯一支持值，Codex 菜单因而只显示“中”等单一选项。
12. 所有模型曾统一使用配置助手生成元数据，导致 OpenAI 原生模型丢失 Codex 自身的显示名称和能力定义。
13. “保存并使用/保存并应用”与双击配置的生命周期并存，导致默认模型保存位置和启动时机不一致。
14. 双击正在使用的配置曾被 UI 直接返回，Codex 未运行时无法从该入口启动。

## 6. 风险与限制

- `/models` 返回的模型是否真实可调用、是否完整，取决于供应商实现。
- 模型目录 JSON 是 Codex 兼容层，Codex 后续版本若改变字段要求，需要重新验证。
- `models_cache.json` 是 Codex 本机缓存，配置助手只读使用且不依赖其必然存在；官方未公开目录内部字段时，以本机当前缓存条目为兼容事实来源。
- 新对话应读取目标配置的启动默认模型；既有对话及对话内临时选择可能继续保留自身会话级状态，这是 Codex 的行为，不属于配置助手配置库状态。
- 自动应用依赖 Codex 的 `Ctrl+Q` 正常退出路径和 Windows 正式启动入口；若异常进程无法正常退出，事务会停止且不写入配置，不会强制结束。
- 供应商是否真正接受低/中/高/超高对应的请求参数仍取决于其 OpenAI 兼容实现；配置助手只修正 Codex 菜单能力声明。
- 外部 `model_catalog_json` 由用户负责；配置助手只保护引用，不接管文件内容。
- API Key 仅在内存中用于身份比较和模型请求；测试、日志和报告不输出其值。
