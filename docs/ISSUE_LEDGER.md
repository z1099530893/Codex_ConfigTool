# 问题台账

本文件汇总本项目的全部已知缺陷及其状态，来源有三类：

1. **继承** —— 前序开发记录（`docs/ai/`）中已登记、由前序 Agent 处理的问题。
2. **实测** —— 用户在实际使用和复测中发现的问题。
3. **自查** —— 本次 Qt 前端移植过程中，由测量工具和对比脚本发现的问题。

状态用词是刻意区分的，不要混用：

| 状态 | 含义 |
| --- | --- |
| **已修复** | 代码已改，且自动化验证通过 |
| **已验收** | 用户在真实环境亲手确认过 |
| **待用户复测** | 代码已改、自动化验证通过，但结论只能由用户在真机上下 |
| **已知未修** | 已定位、已量化，本次有意不修 |
| **不做** | 明确排除，不属于缺陷 |

**本项目的原则是：自动化测试通过不等于缺陷修复。** 涉及窗口、输入、任务栏、系统托盘的缺陷，一律标记为「待用户复测」，直到用户在自己的机器上亲眼确认。历史上正是一次把自动化结果当成完整修复的误报，让窗口问题多绕了三轮（见 `DEV-044`）。

## 一、继承的缺陷

### BUG-004 — 重启 Codex 后系统托盘图标消失

提出：2026-08-27。相关记录：`DEV-004`～`DEV-007`、`DEV-020`～`DEV-027`。

**症状**：通过配置助手重启 Codex 后，Codex 主窗口和任务栏入口出现，但右下角系统托盘没有 Codex 图标，无法通过托盘菜单退出。

**根因（分多层，逐层排除后才定位）**：

- 用 `IApplicationActivationManager` 直接激活 Store 应用，Codex 进程成了配置助手的子进程，单独结束配置助手会连带杀掉 Codex。
- 改用 `explorer.exe` + AppsFolder AUMID 后，进程父子关系正确，但托盘图标仍缺失。
- 只读提取本机已安装 Codex 26.825.5331.0 的 Electron 主进程源码后确认：Store 正式版用**固定托盘 GUID** `e5768d8b-6936-4f45-b1ad-4c5fb414cb35` 创建 `Tray`，`taskkill` 之后该 GUID 在 Explorer 中的注册会残留，导致新实例托盘初始化失败。
- 不带 `/F` 的 `taskkill` 在当前 Codex 版本上并不可靠：`before-quit` 会阻止一般退出，而 Windows 应用菜单的 `Ctrl+Q` 走 Electron `role: quit → app.quit()`，与托盘「退出」汇入同一生命周期。

**修复**：删除 `taskkill` 路径 → 核验并聚焦 Codex 顶层窗口 → 确认前台 PID 属于本次识别的 Codex 进程 → `SendInput` 发送完整 Ctrl/Q 按下抬起序列 → 等待完全退出 → `Shell_NotifyIconW(NIM_DELETE)` 精确清理固定 GUID → 经 AppsFolder 正式入口启动 → 确认新主进程与可见主窗口。

**附带修复**：`DEV-025` 发现旧版 Win32 `INPUT` 联合体只声明了键盘成员，在 64 位 Windows 中生成 32 字节结构，而 `SendInput` 要求包含鼠标、键盘、硬件成员的 **40 字节**原生 ABI，因此系统静默拒绝输入——这才是「窗口已激活但按键注入无效」的真正原因。

**当前状态**：**待用户复测**。`DEV-007` 曾在 2026-08-28 判定为 `ACCEPTED`，但 2026-08-30 用户再次反馈偶发缺托盘图标，该结论随即失效并撤回为 `RETEST`。修复流程已重做，尚未在真机确认。

### BUG-005 — 点击最小化后配置助手自动退出

提出：2026-09-09。相关记录：`DEV-035`～`DEV-044`。

**症状**：v1.4.0 点击自绘标题栏的最小化按钮后，配置助手自动退出，而不是留在任务栏。

**根因**：早期为规避退出问题，在最小化/恢复时切换 `overrideredirect` 并重新注册任务栏样式。这会让 Windows Shell **重新创建**任务栏按钮，产生图标/标题刷新和重复按钮；同时任务栏按钮没有稳定复用同一个顶层 HWND。另外 `PostMessageW` 未声明 64 位 HWND 参数类型，句柄被按 32 位整数截断，最小化消息实际没有生效。

**修复过程（含三次失败返工，值得记录）**：

| 轮次 | 做法 | 结果 |
| --- | --- | --- |
| `DEV-035` | 用顶层 HWND 调 Win32 `SW_MINIMIZE` | 最小化正常，但任务栏图标点击无反应 |
| `DEV-036` | 恢复 `GetParent(winfo_id())` 顶层句柄；补全 `wintypes` 参数类型 | 任务栏图标恢复，但点击仍不能切换显示/最小化 |
| `DEV-037/038` | 原地重新应用 `WS_EX_APPWINDOW`；只移除 `WS_CAPTION`/`WS_THICKFRAME`，保留 `WS_MINIMIZEBOX` | 能力恢复，但动态边框方案在打包版仍导致尺寸递增 |
| `DEV-040/041` | 撤回动态 Win32 边框补偿与自定义 WndProc | 隔离运行曾触发 Python GIL 崩溃，堆栈在注入的 `custom_wndproc` |
| `DEV-043` | 回到稳定 Tk 无边框基线，只在初始化阶段隐藏原生边框 | 连续 10 次最小化/恢复尺寸稳定 `820×500` |
| `DEV-044` | 参考 `Image-Management/qt_app_v20.py`，拖动改用 `WM_NCLBUTTONDOWN/HTCAPTION` | 不再在鼠标移动期间高频调用 `geometry()` |

**关键教训**：`DEV-044` 明确记录「此前将自动化测试结果误报为完整修复」。这是本项目把「待用户复测」单列为一个状态的原因。

**当前状态**：**待用户复测**。

### 用户报告的「是/否」按钮顺序反了

**这是本次移植中最值得记录的一个缺陷**，因为它在代码里完全看不出来。

Tk 的 `pack(side="right")` 把**先** pack 的控件放在**最右**；`QHBoxLayout` 则是从左往右依次追加。两个工具链对「第一个」的定义相反，所以照抄 Tk 的创建顺序会让每一对右对齐按钮**镜像**。

**适用范围是每一个右对齐按钮对**，不只是确认框。

**当前状态**：**已修复**。并已用 `probe_dialog_button_order.py` 在两个前端的独立子进程里逐一比对。

> 该探针本身出过一次假绿：主窗 `withdraw()` 会让 transient 对话框永远不被 map，未 map 的控件 `winfo_rootx()` 返回**顶层窗口**的 x，所有按钮取值相同，排序在相等键上**静默退化成创建顺序**，给出恰好相反的答案。修好后**故意证伪**通过才敢用。教训：**没被证伪过的仪器还不算仪器。**

### 用户报告的侧栏选中色块位置

用户把侧栏选中色块描述为在「最右侧」，但 Tk 的源码和截图都显示它画在**最左侧**。移植版跟的是 Tk 的实际行为。

**当前状态**：**待用户确认**。需要用户对照实际界面确认以哪边为准。

## 三、本次 Qt 移植过程中自查发现的问题

### 3.1 闪烁的根因（本次的核心结论）

**这不是 bug，是结构性差异。**

Tk 顶层窗口没有 backing store：恢复时窗口先被呈现、内容后绘制，中间 1-3 帧由合成器用窗口背景色 `#f3f4f7`（均值 244.7）填充。

逐一排除过的方案：

| 方案 | 结果 |
| --- | --- |
| 把整个视图压平到一个 `Canvas` | 只改善约 33%，仍 8/8 闪 |
| `WS_EX_LAYERED` | **不是变量**，加了也一样闪 |
| `WS_EX_COMPOSITED` | 按**子窗口数**计费（118 个窗口 3 秒 0.3177 s），不是解法 |
| Qt 前端 | **0/8 闪、0/241 空白帧** |

缺的是**一个表面 + backing store** —— 只有 Qt 两者兼备。

**实测对比（同程序、同探针、各 8 轮）**：

| 指标 | Tk | Qt |
| --- | --- | --- |
| 原生子窗口数 | **118** | **0** |
| 闪烁轮次 | **8/8** | **0/8** |
| 空白帧 | **12/241** | **0/241** |

**当前状态**：**已修复**（以新增 Qt 前端的方式），**待用户在本机亲眼确认**。

### 3.2 版面保真 —— 八条硬规则

移植中每条都造成过可见偏差，全部已修复。展开说明与公式见 `prototypes/README.md`：

1. **`pack` 与 `QVBoxLayout` 对余量的处理相反**：Tk 余量留底部，Qt 摊进各间隙 → 页面末尾要 `addStretch(1)`；但**不要**用在切换配置和推荐渠道（那两处有伸缩）。
2. **Tk `pack(side="right")` 与 `QHBoxLayout` 顺序相反** → 见上节。
3. **标签盒子高度：Tk 按 `linespace`，`QLabel` 按 `height()`**，差在「每行」。所需 padding = `(leading + 2) × lines + 6`：常规 `leading=0` → 8px；粗体 `leading=1` → 9px；自动换行每多一行再短 2px，要 pin 高度。**必须补在每一个 label role 上**：漏掉 `#hint`/`#channelUrl` 曾让表格整体上移 9px —— 症状是**邻居元素偏高**，不是「某个标签不对」。
4. **别只看高度，要看字号**：角色没写 `font-size` 会继承基础样式 9pt（Tk 用 8pt bold 画的 `panelHeading` 一直大了一号，1px 高度差只是症状）。
5. **`QLabel.setWordWrap(True)` 不够**：祖先面板若是 `QSizePolicy.Fixed`，会按 `sizeHint()` 给一行高度，把文字**截断在句子中间**。需显式 pin 高度，或让面板垂直策略可增长。
6. **算行数不要拿 `heightForWidth()` 除以字体高**（QSS 的 padding 已含在里面，两行会四舍五入成三行）；用 `QFontMetrics.boundingRect(rect, Qt.TextWordWrap, text)`，它不含 padding。
7. **QSS 渐变 stop 只按 0 或 1 解析**：`stop:0.0303`、`stop:3%` 都会把整条声明**静默**压成纯色（无警告、无日志）。测这类东西**必须并排放一个已知可用的两段式渐变做对照**。
8. **Tk 的 `width=1`（`tk.Label`/`tk.Canvas`）是一个字符宽，不是一像素**（雅黑下 13px）。凡 Tk 用 `width=`/`height=` 的地方一律 `winfo_width()` 量，不要信字面值。

另外三条：**QSS 的 border 加在 padding 之外**（`Treeview.Heading` 补 1px 边框后 35→37px，padding 要退回那 2px 并复测）；**`style.layout()` 要跟 `style.configure()` 一起读**（`Model.TCombobox` 的 `padding=(6,5,34,5)` 是给一个**已被 layout 删掉的箭头**留的位置，真箭头是 `place` 的 28×29 `tk.Canvas`——**空白内边距里没有可见元素 = 上面有手绘东西**）；**Tk 尺寸分上下文**（页面按钮 35px、对话框按钮约 30px、输入框 35px；Qt 的 `APP_QSS`/`DIALOG_QSS` 正好一一对应，别用一套全局值去凑）。

**当前状态**：**已修复**，五页全部对齐（`worst |dy| = 0px`）。

| --- | --- | --- |
| **报告比它描述的产物还旧** | 工具只收一个路径，报告里不记录当时是哪份字节。磁盘上唯一的 `qt-exe` 闪烁报告比 EXE 还旧，却被当成当前构建的结论引用 | **已修复**：引用前先比两个 mtime；预期要重建就写到新路径，旧记录本身就是基线 |
| **最小化状态下读几何量毫无意义** | 图标化窗口报的是「停车位」矩形，820×500 实测 `client [0,0] / frame [160,28]` | **已修复**：断言放恢复之后 |
| **`winapi.taskbar_has_window_title` 在 Windows 11 上不工作** | 它读的是 Win 7-10 的任务栏结构，实测 class 在但**没有任何带文本的按钮子窗口** | **已记录**。它**从未被任何代码调用过**，所以 docstring 里「这是 ground truth」一直没人推翻。**没被调用过的辅助函数不等于能用的辅助函数** —— 信 docstring 前先 grep 调用者 |
| **合成输入被宿主机静默拒绝** | `SetCursorPos` 返回 0 且 `GetLastError` 为 0、`SendInput` 返回 1 但光标不动、`GetClipCursor` 是完整虚拟桌面、未锁屏、前台是真实应用；关掉命令沙箱结果完全一样 | **已诊断清楚，不必再推导**。宿主机级别，与沙箱和构建都无关。**判据是光标在重试之间是否移动**：移动 = 有人在用机器 |
| 同步检查用「自己列过的清单」 | 改成「枚举 `prototypes/` 下所有文件、凡技能目录里同名就比」后才发现 `scripts/tk_visual_tour.py` 是旧快照 | **已修复**：「我同步过的那几个是一致的」是循环论证 |
| 探针在子进程 `import` 失败时仍打印 `ALL DIALOGS MATCH` | **空表上的绿色结论** | **已修复**，并要求故意证伪后才投入使用 |
